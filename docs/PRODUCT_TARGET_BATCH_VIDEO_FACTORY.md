# 产品目标文档：批量短视频工厂 MVP

> 给 Codex 目标模式使用：本文件定义“要做成什么产品”，`docs/CODEX_TARGET_BATCH_VIDEO_FACTORY.md` 定义“工程上怎么实现”。Codex 开发时必须同时读取两份文档，避免只做技术接口而偏离产品价值。

## 1. 产品一句话

面向小红书 / 抖音矩阵运营者和小商家的本地 Agentic 短视频生产工厂：输入多个商品或选题，按平台模板批量生成可人工审核的标题、封面文案、脚本、分镜、素材计划、发布文案、A/B 变体和本地发布包，并为后续成片渲染和数据回流打基础。

## 2. 产品定位

本产品不是：

1. 单点文案生成器。
2. 单条 AI 视频生成器。
3. 剪辑软件替代品。
4. 自动发号 / 自动搬运工具。

本产品是：

```text
商品/选题/素材
  -> 平台模板
  -> Agentic workflow
  -> AI 草稿 + deterministic fallback
  -> 人工审核
  -> 发布包 / 可选成片
  -> 批量变体
  -> 手动指标回填
  -> 复盘下一轮选题和模板
```

核心价值不是“生成一条视频”，而是“稳定、可复用、可测试地生产短视频内容”。

## 3. 首批目标用户

### 3.1 第一优先级：小红书 / 抖音矩阵号运营者

特征：

- 同时运营多个账号。
- 每周需要持续产出大量内容。
- 有商品、素材或选题，但标题、hook、脚本和分镜产能不足。
- 愿意人工审核和微调，不要求完全自动发布。

核心任务：

```text
我有 3-20 个商品/选题，希望快速生成每个平台可用的发布包和测试变体。
```

### 3.2 第二优先级：小商家 / 本地生活商家

特征：

- 有真实商品、服务、门店案例。
- 不会系统写短视频脚本。
- 通常用剪映或外包剪辑。

核心任务：

```text
我想知道这个商品/服务应该怎么拍、怎么说、发什么标题和文案。
```

### 3.3 暂不优先

- 专业影视团队。
- 只想生成 AI 炫技视频的人。
- 需要全自动账号发布和数据抓取的大型机构。
- 只做长视频 / 课程剪辑的团队。

## 4. 核心痛点

1. 从商品到脚本太慢。
   - 用户经常有商品和素材，但没有内容角度。

2. 平台风格不匹配。
   - 小红书需要真实体验、避坑、收藏感。
   - 抖音需要前 3 秒强 hook、短句、高节奏、强 CTA。

3. 同一个商品难以批量测试。
   - 用户真正想测的是标题、封面、hook、脚本结构、卖点顺序。

4. 生产过程不可追踪。
   - 脚本、分镜、素材、版本和数据散落在聊天记录、表格和剪辑软件里。

5. 全自动成片质量不稳定。
   - MVP 应优先产出“可人工审核和剪辑的发布包”，成片渲染作为增强能力。

## 5. MVP 北极星

### 5.1 北极星行为

用户一次提交 3 个以上商品，并在 15 分钟内拿到可审核的批量发布包。

### 5.2 MVP 成功标准

MVP 阶段先用本地测试和人工试用衡量：

1. 单次 batch 至少支持 3 个商品。
2. 每个商品至少生成：
   - 5 个标题。
   - 3 个封面文案。
   - 3 个脚本版本。
   - 1 份分镜。
   - 1 份素材计划。
   - 10 个 A/B 变体。
   - Markdown + JSON 发布包。
3. 无 API key、无外部模型时也能完成上述输出。
4. 小红书和抖音输出风格明显不同。
5. 用户能从 batch report 看懂每个商品生成了什么、文件在哪里、下一步该做什么。

## 6. MVP 功能边界

### 6.1 Must Have

1. 批量输入商品。
2. 批量创建项目。
3. 平台模板选择：小红书 / 抖音。
4. Agentic workflow 节点化执行。
5. 发布包生成。
6. A/B 变体生成。
7. Batch report。
8. 手动指标回填的基础数据结构。
9. 中文模块文档。
10. Go 测试和 smoke 请求。

### 6.2 Should Have

1. 可选 OpenMontage 渲染。
2. render=false / render=true 明确区分。
3. 输出目录稳定。
4. 项目、batch、export 文件可追踪。
5. workflow 节点执行日志或摘要。

### 6.3 Could Have

1. Edge TTS。
2. SRT / ASS 字幕文件。
3. 简单 FFmpeg/Remotion 成片。
4. Web 控制台。
5. Ollama LLM executor。

### 6.4 Non-Goals

本阶段不做：

1. 自动登录和发布到小红书 / 抖音。
2. 自动抓平台指标。
3. 团队权限。
4. 复杂异步任务队列。
5. 云端计费。
6. 完整可视化剪辑器。
7. 多语言跨境模板。

## 7. 关键用户旅程

### 7.1 Batch 生产旅程

```text
准备 3 个商品
  -> 选择平台 xiaohongshu 或 douyin
  -> POST /api/v1/batches/run
  -> 系统逐个创建项目
  -> workflow 生成 brief / scripts / storyboard / material plan
  -> 生成 10 个变体
  -> 导出 publish_package.md/json
  -> 汇总 batch_report.md/json
  -> 用户打开报告审核
```

### 7.2 单项目旅程

```text
POST /api/v1/projects
  -> POST /api/v1/projects/{id}/brief
  -> POST /api/v1/projects/{id}/variants
  -> POST /api/v1/projects/{id}/export
  -> 可选 POST /api/v1/projects/{id}/render/openmontage
```

### 7.3 数据回流旅程

```text
用户发布某个变体
  -> 手动记录 views / likes / saves / comments / completion_rate
  -> POST /api/v1/projects/{id}/variants/{variant_id}/metrics
  -> 后续用于找出更好的 hook / title / script structure
```

## 8. 平台差异化产品规则

### 8.1 小红书模板：xiaohongshu_product_seed

语气：

- 真实体验。
- 朋友分享。
- 避坑。
- 收藏。
- 不硬广。

标题方向：

- 值不值得买。
- 新手避坑。
- 真实体验。
- 被问很多次。
- 适合某类人。

脚本结构：

```text
痛点共鸣
  -> 商品出现
  -> 3 个使用/选择理由
  -> 适合/不适合人群
  -> 收藏/评论引导
```

QA 重点：

- 避免绝对化承诺。
- 保留真实感。
- 标签自然。
- 字幕不宜太长。

### 8.2 抖音模板：douyin_product_hook

语气：

- 短句。
- 直接。
- 前 3 秒强刺激。
- 节奏快。
- CTA 明确。

标题方向：

- 别再乱买。
- 3 秒看懂。
- 这类人适合。
- 买前先看。
- 一个动作判断。

脚本结构：

```text
强 hook / 反常识
  -> 直接展示核心卖点
  -> 快速对比痛点
  -> 适用人群
  -> 明确行动
```

QA 重点：

- 前 3 秒是否抓人。
- 句子是否短。
- CTA 是否明确。
- 分镜是否更快。

## 9. 输出物规格

### 9.1 每个项目输出

建议目录：

```text
data/batches/<batch_id>/projects/<project_id>/publish_package.md
data/batches/<batch_id>/projects/<project_id>/publish_package.json
```

Markdown 发布包必须包含：

1. 商品基本信息。
2. 商品分析。
3. 内容角度。
4. 标题候选。
5. 封面文案。
6. 三个脚本版本。
7. 分镜表。
8. 素材计划。
9. 配音文案。
10. 字幕文本。
11. 发布正文和标签。
12. 10 个变体表格。
13. QA 结果。
14. 人工审核 checklist。

### 9.2 Batch 输出

建议目录：

```text
data/batches/<batch_id>/batch_report.md
data/batches/<batch_id>/batch_report.json
```

Batch report 必须包含：

1. batch id / name / status。
2. 平台 / 模板 / 商品数量。
3. 每个商品的 project id。
4. 每个项目的发布包路径。
5. 成功 / 失败状态。
6. 若失败，失败原因和下一步建议。
7. 下一步操作建议：审核、补素材、发布、回填数据。

## 10. 质量标准

### 10.1 内容质量

每个输出都要尽量做到：

- 像平台原生内容，而不是通用 AI 文案。
- 标题和 hook 有测试差异。
- 脚本可拍摄、可剪辑。
- 素材计划具体，不只写“准备素材”。
- QA 能指出风险，而不是永远 passed。

### 10.2 工程质量

- `internal/workflow` 是主业务流程。
- `internal/agentkit` 体现 tRPC-Agent-Go 迁移路径。
- `internal/engine` 只做应用服务编排。
- `internal/exporter` 负责文件输出。
- `internal/tools` 负责可复用工具能力。
- 新模块必须有中文 `doc.go` 和 `docs/modules/*.md`。

## 11. 产品指标

### 11.1 Activation

- 创建第一个项目。
- 成功跑完第一个 batch。
- 打开 batch_report。

### 11.2 Quality

- 发布包可用率。
- 用户需要重写的比例。
- QA 通过率。
- 用户选择发布的变体比例。

### 11.3 Efficiency

- 3 个商品生成 30 个变体所需时间。
- 单商品从输入到发布包的时间。
- 用户人工编辑时间。

### 11.4 Retention

- 每周 batch 次数。
- 每个用户平均商品数。
- 是否回填指标。

### 11.5 Business

- 用户是否愿意为下一批付费。
- 用户最愿意付费的模块：标题脚本、分镜素材计划、成片渲染、数据复盘。

## 12. 验证实验

### 实验 1：本地 batch smoke

假设：系统可以一次处理多个商品并产出清晰发布包。

设置：

- 使用 `smoke/batch_products_request.json`。
- 至少 3 个商品。
- render=false。

成功标准：

- API 返回 200。
- batch_report.md/json 存在。
- 每个商品都有 publish_package.md/json。
- `go test ./...` 通过。

### 实验 2：平台差异化检查

假设：同一商品在小红书和抖音下会产出明显不同内容。

成功标准：

- 小红书标题更偏种草/避坑/真实体验。
- 抖音标题和 hook 更短、更直接、更强 CTA。
- 单元测试能断言差异。

### 实验 3：人工可用性试用

假设：3 个商品生成 30 个变体后，用户至少能挑出 6 个可轻编辑发布的版本。

成功标准：

- 60% 以上发布包被认为“可用或轻编辑可用”。
- 用户能说出最有价值模块。
- 用户愿意继续让系统处理下一批商品。

## 13. 优先级排序

按早期 MVP 优先级：

1. 批量发布包可跑通。
2. 输出可读、可人工审核。
3. 平台差异明显。
4. 文件路径和 batch report 可追踪。
5. workflow 模块清晰，方便后续接 tRPC-Agent-Go。
6. 指标回填闭环。
7. 可选成片渲染。
8. Web UI。

## 14. 给 Codex 的产品验收口径

Codex 完成后，不只看测试是否通过，还要检查产品是否满足：

1. 用户能一次输入多个商品。
2. 用户能找到每个商品的发布包。
3. 发布包内容足够运营人员直接审核。
4. 小红书和抖音不是同一套文案换标签。
5. Batch report 能指导下一步行动。
6. 没有 API key 时依然可用。
7. 模块文档让后续开发者知道每个模块为什么存在、怎么扩展。
